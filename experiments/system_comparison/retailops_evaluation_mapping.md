# Table 4: RetailOps Evaluation Mapping

This table maps the core comparative dimensions identified across related orchestration literature to specific, completed RetailOps experiments and verified artifacts.

| Evaluation Dimension | Metric | Motivation from Related System Literature | RetailOps Experiment | Evidence Artifact | Limitation |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Service Decoupling & Replacement** | Sibling service code churn ($\text{LOC}_{\text{sib}}$); downstream decision consumption rate | Flowr conceptually discusses modular agent decomposition, but published literature does not quantify the developer effort required to replace an existing service implementation. | **Task 04**: Service Replacement Experiment | `experiments/service_replacement/results.md` | Evaluated on moving average forecasting replacement; does not evaluate swapping proprietary enterprise ERP backends. |
| **Runtime Overhead & Latency** | Process initialization latency ($T_{\text{init}}$); warm call latency ($T_{\text{call}}$); workflow wall-clock latency ($T_{\text{wf}}$) | Workflow systems rarely dissect process spawn overhead from protocol transport latency; WorkflowLLM and Flowr do not measure systems-level IPC costs. | **Task 05**: Deterministic Runtime Benchmark | `experiments/runtime_benchmark/deterministic_summary.json` | Measurements reflect local OS subprocess execution; distributed network MCP latency was not evaluated. |
| **Session Lifecycle Amortization** | Persistent session startup time ($T_{\text{start}}$); persistent speedup factor | Process-per-call tool execution introduces severe startup overhead; persistent pooling is essential for enterprise adoption but rarely benchmarked. | **Task 06**: Persistent MCP Session Evaluation | `experiments/persistent_mcp/summary.json` | Persistent session pooling introduces memory residency trade-offs; tested with 4 concurrent services. |
| **Subprocess Fault Handling & Cleanup** | Failure detection rate ($R_{\text{det}}$); downstream protection rate ($R_{\text{prot}}$); zombie process count | Systems like Flowr address high-level semantic policy governance; systems-level crash recovery and OS resource cleanup are rarely instrumented. | **Task 07**: Fault-Tolerance and Cleanup Evaluation | `experiments/fault_tolerance/summary.json` | Focuses on unhandled exceptions and crash exits; does not implement automated self-healing restart loops. |
| **Architecture Extensibility** | Existing service modification count ($F_{\text{mod}}$, $\text{LOC}_{\text{mod}}$); cross-service dependency count ($D_{\text{cross}}$) | Flowr and WorkflowLLM claim generalizability, but quantitative software engineering metrics for adding new workflow stages are unmeasured. | **Task 08**: Extensibility Evaluation (Supplier Intelligence) | `experiments/extensibility/summary.json` | Evaluated by adding 1 new service (Supplier Intelligence); does not evaluate arbitrary dynamic graph rewrites. |
| **Paired Architectural Isolation** | Paired baseline comparison ratio ($R_{\text{lat}}$); output schema parity | Related literature evaluates against heuristic or foundation model baselines rather than isolating protocol overhead via an identical in-process baseline. | **Tasks 03, 05, 08**: Tightly Coupled Baseline | `baseline/tightly_coupled.py`, `baseline/extended_tightly_coupled.py` | Baseline runs in-process Python calls; cannot scale across multiple machines without network IPC. |
| **Observability & Telemetry** | Execution ID tracking; stage duration logging in ms; automatic secret scrubbing | Enterprise auditability requires tamper-evident decision tracking without exposing API credentials. | **Task 02**: Research Instrumentation | `logs/telemetry.jsonl` | Evaluates local JSONL logging; enterprise centralized database ingestion was not evaluated. |
